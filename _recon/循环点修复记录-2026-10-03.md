> 涉及提交前的工作区改动（尚未提交），自检结果 **16 个套件全部通过**。

## 一、一句话结论

用户反馈「改循环点还是没有效果」。逐层排查后确认：**写入一直是好的**，
问题在于 **TH12 的 BGM 播放引擎根本不读 `thbgm.fmt` 里的 `loop` 字段**。

因此循环点功能被重新实现为**改音频**（拼接），而不是改那个字段。

---

## 二、根因：反汇编 th12.exe

### 证据链

**1. 写入没问题（先排除了这条）**

改循环点后重新解档，`th12.dat` / `th12c.dat` 里的 `thbgm.fmt` 都带上了新值；
`thbgm.dat` 与 fmt 的 `offset`/`end` 首尾严格相接（17/17 条相接，
最后一条结束位置正好等于文件大小）。fmt 结构也逐字段核对无误：

```
+0x00 name[16]        +0x10 offset = 16
+0x14 preload = 12073952   +0x18 loop = 3457440   +0x1C end = 10493952
+0x20 01 00 02 00 44 ac 00 00 10 b1 02 00 04 00 10 00   ← 标准 WAVEFORMATEX
```

**2. 游戏不读它（真正的根因）**

`th12.exe` 的 BGM 播放器在 `0x00453940`–`0x00453AD8`：

```
0x004539B5  CreateFileA(".\thbgm.dat")
0x00453A19  eax = entry[+0x10]   → offset   用来定位文件指针
0x00453A2F  eax = entry[+0x14]   → preload  malloc 这么多字节读进内存
关闭时      free(buf) / Release()
```

fmt 基址 `0x004D0E6C` 在**整个 exe 里只有 9 处引用**，逐条查完都是
「读文件存指针 / 打开时取 offset 与 preload / 关闭时释放」。
用函数边界（int3 填充）切出 2057 个函数做长度受限的数据流跟踪，
**以 `+0x18` 读取 fmt 条目的位置命中 0 处**。

**3. 旁证与交叉验证**

- 原版 18 条轨道的 `preload` **一律大于 `end`**（1.03~1.29 倍）
  → 整条曲子被读进内存后**整块循环播放**，所以 `loop` 是死数据。
- `[th10] 东方风神录` 目录里有一个**独立的** `thbgm.fmt`（953 字节
  = 18×0x34 + 17 字节尾串），字段布局与 TH12 完全一致、18/18 条
  `preload > end` —— 说明格式解读正确，不是我们读错了。

### 这次的教训

前几轮测试全都在验证「值有没有写进磁盘」（都通过了），
但**从没验证「游戏认不认这个字段」**。功能测试通过 ≠ 功能有效。

## 三、修复：用音频拼接真正实现循环

### 原理

设引子 = `[0, L)`、循环体 = `[L, end)`，保存时把音频拼成：

```
[ 引子 ][ 循环体 ][ 引子 ]
 0..L    L..A      A..A+L        （A = 原曲长度）
```

引擎播完 `[0, A+L)` 后回到 0 重放，此时听到的正好是最后那份引子，
它结束处紧接循环体开头 —— 于是音乐无缝进入第二段并无限循环：

```
时间轴:  引子 → 循环体 → 引子 → 循环体 → 引子 → 循环体 → …
听感:    引子 → 循环体 →（无限循环循环体）→ …
```

实现：`thtk/bgm.py` 的 `splice_loop_pcm()`（纯字节偏移，16bit 立体声
按字节切即可，无需解码）。

> **方案的适用前提**
>
> 这套拼接成立的条件是「引擎把整块缓冲从头循环播放」。这一点是**推断**的：
> 已确认的是引擎不读 `loop` 字段、且 `preload` 一律大于 `end`（整条曲子都在
> 缓冲里）；至于循环回卷点具体在 0 还是别处，没有从反汇编里直接读出来
> （DirectSound 的 `DSBPLAY_LOOPING` 语义是回到缓冲开头，与此一致）。
>
> 因此**必须实测验证**：如果游戏里听到的是「引子播两遍再进循环体」，
> 说明回卷点不是 0，那就把拼接改成 `[循环体][引子]` 即可，其余逻辑都不用动。

### 代价（已在界面与文档中如实说明）

- **拼接处是硬切**，乐器会断一下。原曲的 `loop` 值本来就是作曲者标的
  自然衔接点，所以断点通常很轻微，但**绝不是无缝的**。
- **曲长会增加引子那么长**（界面显示「保存后总长」）。
- 循环点在界面上改成了「**引子长度**」的语义，`0` 表示整首从头循环。

### 反复修改不会叠加

第一次给某条轨道设循环点时，把它当时的音频原样存一份到暂存
（`_ensure_bgm_origins()`），之后每次保存都从这份**未拼接的原始音频**
重拼。替换成新音频时这份暂存会同步更新。

## 四、修复过程中自己引入并修掉的 3 个 bug

| # | Bug | 症状 | 修法 |
|---|---|---|---|
| 1 | 第一版拼接写成 `pcm[:L] + pcm[L:]` | 那**等于原音频**，是个空操作，等于没做 | 改为 `intro + body + intro`（末尾补一份引子） |
| 2 | `_drop_bgm_origins(keep=True)` 只护住了删文件，忘了护住清记录 | 反复改循环点会越拼越长：11.5MB → 13.7MB → 17.2MB | `keep=True` 时**直接 return**，什么都不清 |
| 3 | `list_bgm` 里 `pending_loop` 为 `None` 时做除法 | `TypeError`，音乐页整个报错 | 条件改为 `if (loop and eff_bytes)` |

对照测试（`verify_loop_splice.py`）现在会明确验证：
第 7、8 次改循环点后长度仍固定为 `原长 + 引子`，且内容
`== 原始音频按新循环点重拼`。

## 五、其他真实缺陷（排查途中发现）

> 这几条都是**改动之前就存在**的老问题，与本次拼接功能无关。
> 本次拼接功能自己引入的 3 个 bug 记在第四节。

### 5.1 自检脚本会破坏真实游戏目录 ⚠️

`run_all.ps1` 直接在 `TH12_GAME_DIR` 上写。实测**把一份 `th12c.dat`
写坏过**（读档报 `list index out of range`）。

- 已从备份还原原版目录（现为 31,320,247 / 31,185,900 字节，与原始一致）。
- `run_all.ps1` 改为先复制一份到临时目录（`make_game_copy.py`），
  所有套件在副本上跑；退出时清理副本。
- 副本保留原目录层级（`<临时目录>/<原目录名>/`），
  否则「指到上一级自动纠正」那几项测不到。

### 5.2 自检会清空 `config.json`

`Start-TestServer` 每次启动服务器都写 `{}`，跑完自检用户选好的游戏目录就丢了。
改为开始时留备份、结束时原样还原（用 `Copy-Item` 而非 PowerShell 字符串
往返 —— PS 5.1 读环境变量走 OEM 代码页，会把路径里的全角括号 `（）`
变成乱码写回配置）。

### 5.3 循环点超界被静默清零

`rebuild_bgm_dat` 里 `if track.loop > length: track.loop = 0`，
而接口不校验长度：用户看到「循环点已设为 60.00 秒」的提示，
保存后却是 0 —— 表现为「改了没效果」。

现在 `bgm_set_loop()` 当场拒绝：`loop >= 曲长` 报错并说明，
循环体短于 0.5 秒（`MIN_LOOP_SECONDS`）也拒绝。前端同步夹取并提示。

### 5.4 `preload` 可能截断循环体

替换/拼接后的轨道原本写 `preload = length`（比值恰好 1.0），
与原版「预读缓冲覆盖整段音频」的约定不符。改为
`preload = max(int(length * 1.1), length)`，**强制覆盖整条**。

### 5.5 `STATE.fmt` 缓存失效「侥幸正确」

`STATE.fmt = None` 写在 `for key, item in archives.items()` 循环**内部**。
只改循环点、不改归档条目时不会进循环 —— 之前是靠
「`thbgm.fmt` 也算归档条目」才侥幸执行到。已移到循环外。

### 5.6 死代码与过期产物

- 删除 `warm_up_bgm_peaks()`：定义了从未调用；它会在启动时把 400MB
  `thbgm.dat` 顺序读一遍，反而拖慢启动。
- 删除 `release/`（105 MB，构建于 9-27 22:51，**早于循环点修复**，
  留着会让人误以为包含修复）。

## 八、请用户实测

### 实测前的现状

工具实际工作目录 `D:\010-Important-Work\coding相关\[th12] 东方星莲船 (汉化版+日文版)`：

```
th12.dat       32,167,353   (loop=3457440 即 19.60 秒，两个档都是)
th12c.dat      31,186,169
thbgm.dat     408,829,544   ← 大小与原始完全一致
```

那个 `loop = 19.60 秒` 是**旧实现留下的死数据** —— 它写进去了，但引擎不读，
所以 `thbgm.dat` 一个字节都没变。**它不会自动生效**，需要按下面的步骤重新保存一次，
这次才会真的改音频。

（`thbgm.dat` 会因此变大约 10 MB，即引子那 19.60 秒的 PCM。）

### 步骤

1. 重启工具（后端代码变了）。
2. 音乐页选一条曲子，点「▶ 试听」，把 A 标记拖到想要循环的位置，
   点「↺ 设为当前位置」。
3. 看底部待保存条会显示「循环点 X 秒（保存时按此拼接音频，循环体 Y 秒）」。
4. 点「保存到游戏」（重建 `thbgm.dat` 约 400MB，需等一会儿）。
5. 进游戏听：应当是**前奏播一次，之后一直在设定位置循环**。

### 需要知道的两点

- 拼接处会有**一次硬切**（乐器断一下）。
- 这首曲子的**总长会增加「引子」那么长**（界面会显示「保存后总长」）。

### 请特别留意这一件事

听到的效果应该是「**前奏播一遍 → 进入循环体 → 之后一直在循环体里循环**」。

如果听到的是「**前奏播了两遍才进循环体**」，说明引擎的回卷点不是缓冲开头
（见第三节的「方案的适用前提」）。这种情况告诉我一声就行 ——
把拼接顺序从 `[引子][循环体][引子]` 改成 `[循环体][引子]` 即可，
其余逻辑都不用动。
